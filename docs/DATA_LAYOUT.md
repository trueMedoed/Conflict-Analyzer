# Структура снимков и сравнения версий

Пользователь утвердил структуру: **версия игры → сценарий мира → данные и таблицы**. Снимки **1.8.0.13 / CTI_Campaign_HQC_Eden / r0001** и **r0002** содержат 18 баз-источников припасов и помечены `partial`. Первая ревизия сохраняет исходный формат; вторая использует отдельный `Supplies/Harbors.json`. Остальные разделы и сравнение ещё не реализованы.

## Каталоги

Ниже показаны оба частичных формата: исторический schemaVersion 1 в `revisions/r0001/` и schemaVersion 2 в `revisions/r0002/` и далее. Корневой Harbors по просьбе пользователя служит актуальным представлением r0004; старые корневые data.json / world.json остаются данными r0001. Правила отбора данных — в [EXPORT_ALGORITHM.md](EXPORT_ALGORITHM.md).

```text
snapshots/
  README.md
  <game-version>/
    manifest.json
    worlds/
      <scenario-key>/
        world.json
        data.json
        AI-Groups.md
        Supplies.md
        Supplies/
          Harbors.md
        Starting-Bases.md
        Vehicle-Spawns.md
        revisions/
          r0002/
            world.json
            data.json
            Supplies.md
            Supplies/Harbors.json
            Supplies/Harbors.md

changes/
  README.md
  <old-version>_to_<new-version>/
    SUMMARY.md
    worlds/
      <scenario-key>/
        CHANGES.md
```

Обозначения в угловых скобках — параметры схемы, не буквальные имена каталогов. Для `1.8.0.13 / CTI_Campaign_HQC_Eden` собраны только базы-источники припасов в двух ревизиях. `AI-Groups.md`, `Starting-Bases.md`, `Vehicle-Spawns.md`, другие ревизии и сравнения показаны как план: такие файлы ещё не созданы.

Каталоги `snapshots/` и `changes/` находятся в корне репозитория, вне `ME_Conflict_Analyzer/`. Они хранятся в Git. `exports/` остаётся игнорируемым каталогом временных выгрузок и подготовки результатов.

## Назначение файлов

| Файл | Содержание |
| --- | --- |
| `manifest.json` | Версия и канал игры, версия Workbench и анализатора, версия схемы данных, дата сборки в UTC, набор addon и перечень сценариев снимка |
| `world.json` | Имя и путь сценария, GUID ресурса мира, ключ каталога, зависимости и источники, режим анализа, полнота и предупреждения |
| `data.json` | Данные и полнота четырёх разделов: группы ИИ, припасы, стартовые базы и спавн машин; пока нормализованы только базы-источники припасов |
| `AI-Groups.md` | Таблицы групп ИИ, точек спавна, состава и численности, вероятностей и итогов |
| `Supplies.md` | Индекс таблиц припасов и описание охвата; остальные типы точек добавляются по мере анализа |
| `Supplies/Harbors.md` | Базы с `SCR_CampaignSourceBaseComponent`: Summary, происхождение полей, имя source, количество и интервал пополнения; включает аэропорт |
| `Starting-Bases.md` | Кандидаты стартовых баз, координаты, исходные припасы и их генерация |
| `Vehicle-Spawns.md` | Точки появления техники, варианты машин, координаты и настройки спавна |
| `SUMMARY.md` | Сводка сравнения двух снимков: версии и идентификаторы источников, изменения по сценариям, полнота и ограничения сравнения |
| `CHANGES.md` | Добавленные и удалённые объекты, изменения полей и итогов конкретного сценария со ссылками на источники |

## Частичная модель данных — schemaVersion 1

Файлы первой ревизии `world.json` и `data.json` сохраняют `schemaVersion: 1`. `snapshotId` равен `<game-version>/<scenario-key>/<revision-id>`. Текущий манифест имеет schemaVersion 2 и перечисляет версию схемы, анализатор, нормализатор, дату UTC и пути отдельно для каждой ревизии. Он поддерживает записи обеих схем без переписывания данных первой ревизии. Версия игры берётся из нативного чтения; `capturedAtUTC` — время этого чтения, а не построения таблицы. Версия Workbench передаётся оператором и помечается `provided_by_operator`.

В `data.json` базы находятся в `supplies.sourceBases.records`. Запись содержит `source`, `name`, `baseNameLocalizationKey`, `supplyIncomePerCycle`, `arrivalIntervalSeconds`, `arrivalIntervalMinutes` и `provenance`. Имя — `IEntitySource.GetName()`. Количество — `m_iRegularSuppliesIncomeBase`; исходный интервал — `m_iSuppliesArrivalInterval`; минуты вычисляются делением на 60 без целочисленного усечения. Поля компонента читаются через `BaseContainer.Get`; `directOverride=false` означает унаследованное значение или значение по умолчанию.

`source` сохраняет editor source ID, subscene, слой, родительские ID, ближайший prefab и мировые координаты в метрах. Ближайший prefab не объявляется точным ресурсом, задающим унаследованное поле: `definingResource` пока `null` со статусом `unknown`. Локализационный ключ базы сохраняется как исходное значение; перевод и поиск именованной локации ещё не выполняются.

В этой ревизии `supplies.sourceBases.status=extracted` означает извлечение настроек выбранных компонентов, а не проверку всех условий генерации в игре. Раздел припасов и весь снимок имеют `status=partial`. ИИ, HQ, машины и прочие точки припасов имеют `status=not_analyzed`, `records=null`; это не пустые подтверждённые выборки. Нулевой итог допустим только для выполненной и проверенной выборки.

GUID мира, канал игры и полный список загруженных addon пока неизвестны. Манифест отдельно хранит подтверждённые зависимости проектов со статусом `partial`. SHA-256 нативного входного JSON записан в `world.json` и `data.json`; локальные абсолютные пути в архив не включаются. Формальную JSON Schema и модель остальных разделов предстоит добавить.

## Разделённый формат — schemaVersion 2

Первый раздел обычного экспорта реализован для баз-источников: он сохраняет только объекты с `SCR_CampaignSourceBaseComponent` и четыре явных поля, читает сцену вместе с Eden и готовит JSON отдельного отчёта. Широкая диагностика остаётся отдельной командой, её дамп не требуется. Запуск — в [SUPPLY_SOURCES.md](SUPPLY_SOURCES.md); правила расширения — в [EXPORT_ALGORITHM.md](EXPORT_ALGORITHM.md).

Пары файлов: `AI-Groups.json` / `AI-Groups.md`, `Supplies/Harbors.json` / `Supplies/Harbors.md`, `Starting-Bases.json` / `Starting-Bases.md`, `Vehicle-Spawns.json` / `Vehicle-Spawns.md`. Другие таблицы припасов получают собственные пары после фактического анализа. `Locations.json` хранит используемые именованные локации для связи по ID; он создаётся после реализации этого анализа.

В `r0002` `Supplies/Harbors.json` имеет `kind=supply-source-bases-report`, `count` и `records`; поля записей соответствуют модели source base выше, добавлены `enabled`, путь мира subscene, статусы значений и предупреждения. Исходное поле хранится в `provenance.rawValue`; неизвестное значение или необходимость анализа fallback обозначаются `unknown`, не нулём. Нативный вход имеет `kind=supply-source-bases` и только целевые поля.

Каждая таблица генерируется из своего JSON. Общие метаданные находятся в `world.json`; корневой `data.json` имеет `kind=conflict-world-index`, `sections` с путями и полнотой и не дублирует записи. Несобранные разделы обозначаются `not_analyzed`; пустые файлы для них не создаются.

Новый формат находится в `revisions/r0002/`, ссылки внесены в манифест. Опубликованный `r0001`, его schemaVersion 1 и данные сохраняются. Старый `Convert-SupplySources.ps1` ниже описан для чтения прежней диагностики; новый `New-SupplySourcesReport.ps1` работает с целевым входом schemaVersion 2. Перенос в архив и обновление манифеста пока ручные.

## Идентичность сценария и объектов

Каталог обозначает сценарий, например `CTI_Campaign_HQC_Eden`, а не только остров `Everon`: несколько сценариев могут использовать одну местность. Отображаемое название не используется как единственный идентификатор.

В метаданных сохраняются путь и, когда разрешён, GUID ресурса мира. Неизвестный GUID явно обозначается. Ключ каталога должен быть безопасным для файловой системы и однозначным; при совпадении имён нужен устойчивый суффикс. Для сравнения сценарий связывается по идентичности ресурса, а не только по названию папки. Смену GUID / пути следует разрешать явным сопоставлением, а не угадывать.

Объекты сравниваются по стабильным идентификаторам источника. Если ID недостаточно, требуется документированный ключ из сценария, слоя, иерархии и ресурса; ID prefab сам по себе не различает несколько его экземпляров. Номер строки, порядок обхода и текущие координаты не должны быть единственной основой ключа. Неоднозначное сопоставление нужно показать в отчёте.

Текущий `id` записи — `subscene/layer/sourceId`. Эти editor ID повторились в двух прогонах одной версии ресурсов, но устойчивость между релизами игры не проверена. До такой проверки они являются предварительными ключами; автоматическое сравнение на них ещё не реализовано.

## Сборка снимка

1. Выполнить анализ в `exports/`, записать метаданные, данные и предупреждения. Для первого раздела преобразовать проверенную нативную диагностику командой ниже.
2. Проверить JSON, полноту разделов и согласованность идентификаторов; построить Markdown-таблицы из этого же `data.json`.
3. После проверки сохранить результат в `snapshots/<game-version>/worlds/<scenario-key>/` и дополнить манифест версии.
4. Просмотреть diff и сохранить снимок в Git. Каталоги версий и JSON создаются только для фактически полученных данных.

Markdown-таблицы генерируются из JSON. Исправления данных нужно вносить в источник или модель анализа, затем пересобирать таблицы. Пустой раздел с неизвестными данными нельзя выдавать за подтверждённое отсутствие объектов.

```powershell
.\tools\Convert-SupplySources.ps1 `
  -DiagnosticsPath .\exports\HQC_Eden_Diagnostics_1.8.0.13.json `
  -OutputDirectory .\exports\HQC_Eden_SupplySources_r0001 `
  -WorkbenchVersion 1.8.0.13
```

Скрипт валидирует метаданные, уникальность ключей и обязательные числовые поля, сохраняет JSON, затем строит Markdown из сохранённого `data.json`. Неизвестные обязательные значения, отрицательный доход или неположительный интервал требуют дополнительного анализа и приводят к отказу импорта. Это преобразование не читает мир повторно и не раскрывает отсутствующие в диагностике конфиги. `manifest.json` дополняется вручную после проверки; автоматическая запись архива пока не реализована.

Опубликованный снимок сохраняется как неизменная точка сравнения. Первая ревизия `r0001` лежит непосредственно в каталоге сценария. Повторные ревизии размещаются в `revisions/r0002/`, `revisions/r0003/` и далее с теми же именами файлов. Они получают собственные `snapshotId`, `revisionId` и `revisionReason` в `world.json`; `-RevisionId` задаётся при подготовке импорта, причину пересборки нужно записать до публикации. Манифест версии дополняется ссылками, прежние файлы сценария не заменяются. Скрипт отказывается писать в любой существующий выходной каталог.

## Сравнение

- Сравнивать выбранные снимки и явно записывать их идентификаторы или Git-коммиты в отчёте, а не брать молча «последний» результат из папки.
- Сначала проверять версии схемы, состав addon, режим анализа и полноту. Изменение анализатора или окружения может менять результат независимо от игры.
- Сопоставлять нормализованные значения и стабильные ключи; порядок строк в таблицах не является изменением мира.
- Показывать добавление, удаление и изменение объектов, отдельно перечислять неполные и несопоставимые данные.
- Если сценарий или раздел не анализировался, обозначать это как отсутствие данных, а не как удаление всех его объектов.
- Сохранять отчёты в `changes/<old-version>_to_<new-version>/`. При повторных сравнениях использовать уникальную ревизию отчёта; существующий отчёт не перезаписывать молча.

## Частичная ревизия r0003 — вместимость аэропорта

`revisions/r0003/` использует schemaVersion 2 и содержит `Supplies/StorageCapacity.json` / `.md`, `Supplies.md`, `world.json` и индекс `data.json`. Канонический JSON хранит две группы хранилищ, пять физических контейнеров, два исключённых из суммы виртуальных представления, исходные поля и общий итог 4000 припасов. Охват явно ограничен одной выбранной базой; доход, ИИ, HQ, машины и локации в этой ревизии не пересобирались. `r0001` и `r0002` сохраняются. Команда и алгоритм — [STORAGE_CAPACITY.md](STORAGE_CAPACITY.md).

## Актуальная таблица и сохранение r0001

По явному запросу пользователя корневой `Supplies/Harbors.md` обновлён: добавлен столбец вместимости из r0004. Он является Markdown-представлением канонической таблицы `revisions/r0004/Supplies/Harbors.json`; ссылки на JSON, состав и метаданные направлены в r0004. Корневые `data.json` / `world.json` сохраняют исторические данные r0001 и не служат источником нового столбца.

Все четыре первоначальных файла r0001 скопированы без изменения содержания в `revisions/r0001/`; манифест направляет историческую ревизию туда. r0002 и r0003 не изменены. r0004 хранит отдельные Harbors.json и StorageCapacity.json, Markdown каждого отчёта, общий индекс и метаданные двух входов. Доход r0002 и новый обход вместимости имеют отдельные время UTC и SHA-256. Архив не выдаёт повторное чтение вместимости за новый сбор дохода.
